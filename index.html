The Pedigree workbench

Draw a family in Pedigree Studio, then turn the drawing into the files other people and other programs need: PED files for linkage programs, and the GA4GH Pedigree and Phenopackets files for sharing a family's pedigree and findings in the international standard. The tools for this are our Python packages, which run here in your browser – by pointing and clicking in the Tools tab, or as commands in the Terminal and code in the Notebook.

The formats, and the tools between them

The drawing is in the middle. Each arrow is a tool that turns one kind of file into another; click it to open that tool, or click a box to see what can be done with that kind of file.

Everything stays on this computer

Pedigree Studio and Python run inside this web page. Your drawings and files are kept in this browser, on this computer, and are not sent anywhere. The one exception is when you ask the tool Match conditions to terms to search EBI's Ontology Lookup Service: then the names you search for (not the drawing) go to EBI. Privacy has the details; Your files says how to keep copies.

A first session

Ten minutes to see what the workbench is for, using one of the example families. Each step has a button that does it for you.

1 · Open a drawing

The Studio tab is Pedigree Studio. Open the Okafor family, one of the examples: four generations, with twin boys who have had hearing loss from birth, whose parents are cousins, and their grandmother, who has had breast cancer.

The bar above the drawing says which file the drawing belongs to. An example cannot be changed, so it opens as a drawing that is not in a file of yours yet: change it as you like, and use Save as… to keep your version in ~/pedigrees. The Studio's own toolbar and its ? button explain the drawing itself.

2 · Give its conditions ontology terms

The colour key names two conditions. A GA4GH file names conditions by ontology terms rather than by free text: diseases by the Mondo Disease Ontology, signs and symptoms by the Human Phenotype Ontology (HPO). The examples come with a terms file that matches them already; for a family of your own you make one with the Match conditions to terms tool (how).

3 · Convert it

The Tools tab has a form for each of our tools. Drawing → GA4GH Pedigree and Phenopackets writes the family as a GA4GH Pedigree and a Phenopackets Family. The button below opens it with the drawing and the examples' terms file (/data/examples/example-terms.json) chosen; press Run. The first run starts Python in your browser, which takes a few seconds (and downloads about 10 MB the first time).

Under the form, The same in the terminal, and in Python shows exactly what the tool runs – a command for the Terminal tab and code for a notebook – so that you can do the same again without the form.

4 · Check the result

The files it writes appear under the result, in ~/results. Check next to a file checks it against the standards, the way the GA4GH's own validator does, and says how to fix anything wrong.

5 · Back to a drawing, or on to a PED file

  • GA4GH or Phenopackets → drawing draws a GA4GH file in Pedigree Studio – one made here, or one someone has sent you.
  • Drawing → PED or MPED writes the PED file that linkage programs read.

6 · Keep your work

Everything you make is kept in this browser on this computer. To keep it anywhere else, download it: a file's Download button, or My files → Download all my files (.zip) at the top right. Your files has the details.

Share a family in the GA4GH standard

From a drawing to files you can send to a collaborator, a registry or another program: a GA4GH Pedigree and a Phenopackets Family. The buttons use the Okafor family, one of the examples; with a family of your own, choose your drawing instead.

Which of the two files to send

The Phenopackets Family is Phenopackets version 2, an approved GA4GH standard: send it to anything that reads Phenopackets. The GA4GH Pedigree holds the whole family, with every relationship named by a kinship term, in the form proposed for the GA4GH Pedigree Standard, which is still being written. If you are not sure what the recipient reads, send both. The GA4GH Pedigree explains the difference.

1 · The drawing

Draw the family in the Studio tab, or open the drawing you have. Every condition needs a colour, and a name in the colour key (the Studio's Key button): the name is how the tools know what the colour means. Save the drawing among your files with Save as…; the tools work on saved files.

Whatever you write under the symbols – names, ages, notes – stays in the drawing. The files name people by their pedigree numbers (I-1, II-3, IV-3), unless you choose otherwise in step 3.

2 · Terms for the conditions

A GA4GH file names a condition by an ontology term: a disease by its Mondo term, a sign or symptom by its HPO term. Match conditions to terms finds them for the conditions in the drawing's key and keeps your choices in a terms file. For each condition, choose whether it is a disease or a sign, press Suggest, pick the right term, and Save.

The examples come with a terms file that has these already, /data/examples/example-terms.json, so with the Okafor family you can skip this step. Give the conditions ontology terms goes through it in more detail.

3 · Convert the drawing

Drawing → GA4GH Pedigree and Phenopackets writes the two files. Choose the drawing and the terms file. Under the terms file, a table shows the term each condition will get; a condition without one is left out of the files, so match it first. Then press Run.

It writes ~/results/okafor_ga4gh-pedigree.json and ~/results/okafor_phenopackets-family.json. In them is everyone in the drawing with their sex, whether they are alive, and their conditions as terms; the relationships between them; and the proband. What the files have no place for, such as a pregnancy or a symbol that stands for several people, is written in the GA4GH Pedigree's narrative, and the tool notes it under the result.

4 · Check the files

Check beside a file (or Check against the standard in the Tools tab) checks it as the GA4GH's own validator would, and for a GA4GH Pedigree checks the family as well. It should say Valid. Errors make a file invalid; warnings are worth reading; notes are for information, such as an ontology release that was not recorded. The examples were made with this tool, so you can try the check on them now:

5 · Look at what is in them

Look inside a GA4GH file shows a file as a table: each person, their sex and status, and their terms, then the relationships. It is the quickest way to make sure the files say what you meant.

6 · De-identify before the files leave you

De-identify gives everyone a new id (IND-0001, IND-0002 …) everywhere in the file, and takes out dates of birth and other ids. It can also write a key from the old ids to the new ones: keep the key, and the drawing, apart from what you share.

What de-identifying does not do

It removes what the file says directly. A family can still be recognised from what is left – a rare condition, the shape of a large family, ages – so whether a file is safe to share is a judgement for you, and for your institution's rules on sharing patient data.

7 · Download them

Each file under a result has Download. To take everything at once, use My files → Download all my files (.zip) at the top right.

The same in the terminal

Every step is a command, so the whole job can be done again in one go:

Make a PED file for a linkage program

Linkage and association programs read pedigrees as PED files: one line per person, with their parents, sex and whether they are affected. There are two ways to make one from a drawing, which differ in how people are named and in how they deal with more than one condition.

From the drawing

1 · Write the MPED file

Drawing → PED or MPED writes a PED file for a drawing with one condition, and an MPED file – a PED file with a column for each condition – when it has more.

It checks what it wrote with mpedtools straight away and says if anything is wrong.

2 · Check the ids

studio2ped names each person by the text under their symbol (or by Pedigree Studio's own id, such as p-ggf, when there is none). In the Okafor family that gives Grace_78 and Emeka_d_70: names. Two people with the same text get the same id, which the check reports as an error. If the file is to leave you, change the labels in the drawing first, or take the other route below.

3 · One condition at a time

Most linkage programs read one condition at a time. Take one condition out makes a plain PED file for one column of the MPED file (or for each, if you leave the condition empty). A plain PED file has no code for a carrier, so carriers become unaffected (1).

Through the GA4GH files

First write the GA4GH files (Share a family in the GA4GH standard, steps 1 to 3). Then GA4GH → PED, table or YAML makes the PED file, with the pedigree numbers as ids.

Make it from the Phenopackets Family: its pedigree records who is unaffected (1) as well as who is affected (2). A GA4GH Pedigree records only the conditions people have, so a PED file made from it marks everyone else 0, unknown. In the Okafor family, affected means having either condition – the grandmother with breast cancer and the twins with hearing loss – which is not what a linkage analysis of one of them wants: for that, take the first route.

The same in the terminal

studio2ped /data/examples/okafor.studio.json -d ~/results -o okafor
mpedtools validate ~/results/okafor.mped
mpedtools extract ~/results/okafor.mped Hearing_loss_from_birth -o ~/results/okafor_hearing.ped
phenotk convert /data/examples/okafor_phenopackets-family.json --to ped -o ~/results/okafor-numbers.ped

PED and MPED files describes the columns and codes.

Draw a PED file you have been sent

A PED file is hard to read as a family. Drawn in Pedigree Studio it can be checked at a glance, finished with what the PED file leaves out, and saved as a picture or converted on to the GA4GH files. The example is the PED file of the Lynch family, in which several people have had bowel or pancreatic cancer.

1 · Add the file

Add the file to your files: My files → Add files from my computer… at the top right, or From my computer… under the file box of the tool in the next step, which puts it in ~/data. The workbench knows a PED file by its ending, .ped or .fam (PLINK's name for the same six columns), and an MPED file by .mped: rename a file that ends otherwise.

2 · Draw it

PED or MPED → drawing lays the family out generation by generation and fills in the affected people (status 2). Choose the colour, and whether to fill the whole symbol or the left half, or to shade with a pattern. An MPED file's conditions each get a colour of their own.

The drawing is saved in ~/pedigrees. Open the drawing in Studio, under the result, shows it; with the box ticked, Pedigree Studio's Tidy lays it out afresh as it opens, which usually gives the neatest drawing.

3 · Finish it in the Studio

A PED file says only who the parents are, the sex and the affected status, so the drawing has only those. In the Studio you can add the rest:

  • The condition's name. The colour key calls it Affected (or, from an MPED file, by its column name). Click the key and type the condition's name, so that the drawing can be matched to terms and converted.
  • Who has died, twins, adoptions, pregnancies, a proband: select a person or a line and use the panel.
  • Labels. Each person is labelled with their id from the PED file; add ages or notes under it if you like.

Then Save in the bar above the drawing. Pedigree Studio's File menu exports a picture (PNG or SVG) to your computer.

Draw a GA4GH or Phenopackets file

A GA4GH Pedigree or a Phenopackets Family drawn in Pedigree Studio, with each condition in the colour key under its term. The drawing can be changed and converted back, and the terms come back with it.

1 · Add the file

Add it with My files → Add files from my computer…, or with From my computer… under the file box of the tool. The workbench tells GA4GH files apart by what is in them, whatever they are called. If it shows a file as plain JSON, it does not recognise it as a GA4GH file; Upgrade a file from an older tool may still be able to read it.

2 · If it was made by an older tool, upgrade it

Files made by studio2ga4gh 0.3 or abusua2ga4gh 0.2 are not in the standard form, and the tools refuse them with a message that says so. Upgrade a file from an older tool rewrites such a file once, in the standard form, and lists what it changed and anything it could not do.

The older files often name conditions without a term. The upgrade lists them; Fill in missing terms gives them their terms from a terms file (how). The drawing does not need them – a condition without a term is drawn with its name – but the GA4GH files do. A GA4GH Pedigree from studio2ga4gh 0.3 recorded only whether people were affected, not by what: draw from the Phenopackets file made with it instead, which has the conditions.

To find out whether a file needs upgrading, look at its summary in the Tools tab (the More… button beside a file): it says Older form when it does.

3 · Draw it

GA4GH or Phenopackets → drawing lays the family out from its relationships and gives each condition a colour, named in the key with its term, such as breast cancer [MONDO:0007254].

Under the result, Open the drawing in Studio shows it, laid out afresh by Pedigree Studio's Tidy if the box is ticked.

4 · Check the drawing

How much of the family comes back depends on the file:

  • From a GA4GH Pedigree: everyone, the couples (consanguineous and separated ones too), twins, adoptions, who has died, and the pregnancies and losses its narrative records.
  • From a Phenopackets Family: everyone in its pedigree, with their parents, sex and conditions. A Family's pedigree is a PED file in another form, so it has no twins and no adoptions: draw from the GA4GH Pedigree when you have one.

People are labelled with their ids, except ids that are pedigree numbers such as II-3, since Pedigree Studio numbers the generations itself. Pedigree Studio draws children from couples, so a child with only one parent in the file is given an unknown parent as the other.

The same in the terminal

pedigree-ga4gh upgrade /data/examples/older/studio2ga4gh-0.3_phenopackets-family.json -o ~/results/upgraded_phenopackets-family.json
phenotk normalise ~/results/upgraded_phenopackets-family.json --mapping /data/examples/example-terms.json --no-online -o ~/results/upgraded_phenopackets-family.json
pedigree-ga4gh validate ~/results/upgraded_phenopackets-family.json
ga4gh2studio ~/results/upgraded_phenopackets-family.json -o ~/pedigrees/upgraded.studio.json
studio --tidy ~/pedigrees/upgraded.studio.json

Check a GA4GH file, or update an old one

The check reads a GA4GH Pedigree, a Phenopackets Family, Cohort or single Phenopacket, and says whether it is correct and how to fix what is not. Use it on files you make before sending them, and on files you are sent before relying on them.

1 · Check the file

Check against the standard takes one file. The answer comes first – Valid or Not valid – then a table with a line for each finding: what is wrong, where in the file (a path such as individuals[4].metaData), and how to fix it.

  • Errors make the file invalid: other software may refuse it, or read it wrongly.
  • Warnings are things that are allowed but probably mistaken, such as a mother recorded as male.
  • Notes are for information, such as an ontology release that the file does not record.

The checks are those of the Phenopackets version 2 schema and of phenopacket-tools, the GA4GH's own validator, with the GA4GH Pedigree's on top: KIN terms, people named in relationships, parents' sexes, loops of ancestry. Check against the standard lists them.

3 · Upgrade an older file

Upgrade a file from an older tool rewrites the file in the standard form and lists every change, and anything it could not do – usually conditions without a term. Under the result, Check the upgraded file checks it again.

Among the things it corrects in files from abusua2ga4gh 0.2: names inside subject, which the standard has no place for; a sperm donor written as KIN:039, which is KIN's term for a gestational carrier; and carriers given the HPO term HP:0032500, which is Exacerbated by tobacco use. What it cannot tell from the file it leaves, and says so: abusua2ga4gh wrote foster and social parents as adoptive parents, and only the free-text note that it keeps in the narrative says which they were. The GA4GH Pedigree lists what was wrong with the older files, and why.

4 · Give the remaining conditions their terms

If the upgrade could not give a condition its term, Fill in missing terms can, from a terms file or by looking the name up (Give the conditions ontology terms). Then check the file once more.

The same in the terminal

pedigree-ga4gh validate /data/examples/older/abusua2ga4gh-0.2_phenopackets-family.json
pedigree-ga4gh upgrade /data/examples/older/abusua2ga4gh-0.2_phenopackets-family.json -o ~/results/abusua_phenopackets-family.json
pedigree-ga4gh validate ~/results/abusua_phenopackets-family.json

pedigree-ga4gh validate ends with exit status 0 for a valid file and 1 for an invalid one, so a script can use it.

Give the conditions ontology terms

GA4GH and Phenopackets files name each condition by a term from an ontology, so that software and people everywhere read it the same way: a disease by the Mondo Disease Ontology, a sign or symptom by the Human Phenotype Ontology (HPO). This walkthrough finds the terms for a drawing's conditions, and fills in the terms that an existing file lacks.

For a drawing: Match conditions to terms

1 · Choose the drawing

The tool lists the conditions in the drawing's colour key, with how many people have each. If you keep a terms file for a project, start from it: conditions it has already are filled in, and new matches are added to it.

2 · Choose where to search

  • EBI's Ontology Lookup Service searches the latest releases and ranks matches well. It needs the internet, and it sends EBI the words you search for – the condition's name, not the drawing.
  • Copies of the ontologies on this computer work without the internet and send nothing. The HPO can be downloaded from the tool (about 11 MB, into ~/ontologies). Mondo's file is about 50 MB and its host does not let web pages download it: download mondo.obo with your browser from Mondo's download page, then add it with From my computer…. The first search of a file reads all of it, which takes some seconds.

3 · Match each condition

For each condition, say whether it is a disease (Mondo) or a sign or symptom (HPO) – the tool guesses from the name – and press Suggest. Each suggestion shows the term's id and label, whether its label or a synonym matched, a score, and the term's definition. Choose the one that is right; if none is, change the words and search again. If you know the id already, type it and press Use this id: it is looked up, so that its label and release are recorded.

Choosing a term

Choose the most specific term that is true of everyone with the condition in this family. Hearing impairment (HP:0000365) is true of the Okafor twins; if their hearing loss is known to be sensorineural, Congenital sensorineural hearing impairment (HP:0008527) says more. Use a Mondo term when there is a diagnosis, and HPO terms for features without one. Read the definition: two terms can share a name, as breast cancer (MONDO:0007254) and breast carcinoma (MONDO:0004989) nearly do.

4 · Keep the matches

Save writes the terms file, ~/terms/price-terms.json for the Price family. Tick Also write the ids into the drawing's colour key to make a copy of the drawing whose key reads Breast cancer [MONDO:0007254]: a drawing like that carries its terms wherever it goes, and converts without a terms file. Then Next opens Drawing → GA4GH with the drawing and the terms file chosen.

For a GA4GH file: Fill in missing terms

Files from older tools, or from elsewhere, may name conditions without their ids. Fill in missing terms gives each one the id from a terms file, matching the names without regard to case. It can also look up names the terms file does not have, and use the best match when it is close enough (the threshold: 1 is an exact match). What it decided goes in a log beside the new file, ….normalised.log.json.

A file made by an older tool must be upgraded first, and the tool says so if it needs to be. To try it: upgrade the older example, then fill in its terms from the examples' terms file (the tool chooses your newest file, which is the upgraded one).

A terms file

A terms file is a small JSON file: each condition's name in the drawing, with its term and the release of the ontology it came from. You can write one by hand, too; an id alone is enough.

{
  "Breast cancer": {"id": "MONDO:0007254", "label": "breast cancer", "version": "2026-10-06"},
  "Hearing loss from birth": {"id": "HP:0000365", "label": "Hearing impairment", "version": "2026-09-01"},
  "Ovarian cancer": "MONDO:0008170"
}

One terms file can serve many drawings: the names are matched without regard to case. Ontology terms and terms files has more.

The same in the terminal and in Python

There is no command that reads a drawing's key and asks about each condition with the mouse; that is what the tool is for. A terms file is used by:

studio2ga4gh /data/examples/price.studio.json -t /data/examples/example-terms.json -d ~/results
pedigree-ga4gh upgrade /data/examples/older/studio2ga4gh-0.3_phenopackets-family.json -o ~/results/older_phenopackets-family.json
phenotk normalise ~/results/older_phenopackets-family.json --mapping /data/examples/example-terms.json --no-online -o ~/results/older.normalised.json

hponorm and mondonorm, the programs behind the searches, match the names in a GA4GH or Phenopackets file by asking about each one as they go. This terminal cannot answer their questions, so here they stop at the first one; they can take their answers from a file instead, whose names are in lower case: hponorm FILE.json --mapping answers.json --auto-remembered -o OUT.json. In Python, their searches are these:

from hponorm.ols import OlsClient            # EBI's Ontology Lookup Service (online)
for c in OlsClient().search("hearing loss from birth", limit=5):
    print(c.id, c.label, c.score)

from mondonorm.mondo import MondoIndex      # a copy of Mondo on this computer
index = MondoIndex.load("/home/user/ontologies/mondo.obo", allow_download=False)
for c in index.search("breast cancer", limit=5):
    print(c.id, c.label, c.score)

The two GA4GH files carry the same family in two ways. This tool turns either into the other – for a file someone has sent you in only one of the forms, for example.

Writes a GA4GH Pedigree, a Phenopackets Family, Cohort or Phenopacket in another format: a PED file for linkage programs, a table of people and their terms, YAML, or JSON Lines.

A PED file

YAML
The same document, in YAML instead of JSON.
JSON Lines
One Phenopacket on each line, for programs that read many at a time.

Match conditions to terms

Finds the ontology term for each condition in a drawing's colour key – a Mondo term for a disease, an HPO term for a sign or symptom – and keeps your choices in a terms file, which Drawing → GA4GH reads. The searches are those of hponorm and mondonorm.

On the page

1 · The drawing
Its conditions are listed under 3, with how many people have each. Start from a terms file fills in the conditions it has already; the matches you make are added to it when you save.
2 · Search in
EBI's Ontology Lookup Service (online, the latest releases, the best ranking) or copies of the ontologies on this computer (offline). For the second, choose hp.obo and mondo.obo among your files: the HPO can be downloaded from here into ~/ontologies, and Mondo's file is downloaded with your browser from its download page, then added with From my computer….
3 · The conditions
For each one: a disease (Mondo) or a sign or symptom (HPO) – guessed from the name, so check it – the words to search for, and Suggest. Up to six suggestions come back, each with its id, label, what matched (the label or a synonym; from EBI's service, its own ranking), a score out of 100 and the definition. Choose one, or type an id and press Use this id. Suggest terms for all searches for every condition not matched yet.
4 · Keep the matches
Save writes the terms file (~/terms/drawing-terms.json). With Also write the ids into the drawing's colour key, it also writes a copy of the drawing, ~/pedigrees/drawing-with-terms.studio.json, whose key reads Breast cancer [MONDO:0007254]. Next opens Drawing → GA4GH with the drawing and the terms file chosen.

What is sent where

With EBI's service, the words you search for and the ids you type are sent to EBI (www.ebi.ac.uk); nothing else is, and not the drawing. With copies on this computer, nothing is sent anywhere. Downloading the HPO here fetches hp.obo from the HPO's repository on GitHub.

Good to know

  • The first search of a local file reads all of it: a few seconds for the HPO, longer for Mondo. The local search ranks less well than EBI's: if the term you expect is missing, try other words.
  • A term's release is recorded with it in the terms file, and goes into the GA4GH files' metaData, so that anyone can tell which version of the ontology the term came from.
  • A typed id is looked up when it can be. If it cannot (no copy of that ontology here, or no answer from EBI), it is used as typed, labelled with the condition's name, and the release is left out.
  • An id written in the key itself (Condition X [MONDO:0009061]) counts as matched.

Give the conditions ontology terms walks through it, with advice on choosing a term.

In Python

There is no command for this page: hponorm and mondonorm work on GA4GH and Phenopackets files, asking about each name as they go (the terminal cannot answer them, so there they take their answers from a file). Their searches can be used in a notebook:

from hponorm.hpo import HpoIndex            # a copy of the HPO on this computer
index = HpoIndex.load("/home/user/ontologies/hp.obo", allow_download=False)
for c in index.search("hearing loss from birth", limit=6):
    print(c.id, c.label, c.score)

Fill in missing terms

Gives an ontology id to every disease and phenotype in a GA4GH or Phenopackets file that has a name but no id, from a terms file or by looking the name up. It also writes the file in the standard form, with the ontology resources its terms need.

The form

The file
A GA4GH Pedigree, a Phenopackets Family, Cohort or Phenopacket. A file from an older tool must be upgraded first.
Terms file
Names and their terms (terms files). The names are matched without regard to case, and the terms file's releases are recorded in the file's resources.
Look up names without a term
No (the terms file only), or on EBI's Ontology Lookup Service (online), or in copies of the ontologies on this computer (choose hp.obo and mondo.obo).
Accept a looked-up match from
How close the best match must be, from 0.5 to 1 (1 is exact). A name whose best match is less close is left without a term, and listed. A terms file's entries are always used.
Save as
~/results/name.normalised.json, with a log of every decision beside it, ….normalised.log.json.

Nothing is guessed: a name that neither the terms file nor a close enough match gives a term keeps its empty id, and the summary lists it. Look at the log before you rely on a looked-up match.

A term goes where its kind belongs: older tools wrote every condition as a disease, so a “disease” that is given an HPO term (Hearing loss from birth, HP:0000365) moves to the phenotypic features, and a phenotype given a Mondo term moves to the diseases. The summary notes each move.

--no-onlinethe terms file only: no look-ups
--backend ols|local, --hpo-file, --mondo-file, --thresholdwhere to look names up, and how close a match must be

Check against the standard

Checks a GA4GH Pedigree, a Phenopackets Family, Cohort or Phenopacket, and says for each problem what it is, where it is in the file, and how to fix it. It needs nothing but the file: no Java, no internet.

What is checked

As the GA4GH's own validator does

phenopacket-tools is the GA4GH's validator for Phenopackets. The check applies its rules:

  • The Phenopackets version 2 schema: the fields each part may have and must have, their types, the allowed values (sex, vital status, progress status …), the groups of which exactly one must be given, and minimum lengths and counts. A field the schema does not have is an error, because Phenopackets readers reject it.
  • The ontologies: every term's id is a CURIE (PREFIX:ID), and every prefix used is declared among the resources in the file's metaData.
  • Values: ages are ISO 8601 durations (P45Y), dates and times are in the right form.

And for a GA4GH Pedigree

  • Every id in the relationships and the index patients is the subject of one of the individuals, and no two individuals share an id.
  • Every relation is a current KIN term, written with KIN's own label; retired codes from earlier drafts of KIN are reported.
  • No one is related to themselves; a biological mother is female and a father male; no one has more than two genetic parents; no one is their own ancestor.

And one mistake of older files

  • HP:0032500 used for a carrier. It is valid in form – a real HPO term – but it is Exacerbated by tobacco use.

The check does not look terms up, so it cannot tell whether a term is the right one for the person: only that it is well formed and declared.

The result

Valid or Not valid, then a line for each finding: errors (the file is invalid), warnings (allowed, but probably a mistake), and notes (for information). Each has a code, such as empty-term-id, the place in the file, and how to fix it. A file from an older tool is recognised as such, with a button to upgrade it. Check a GA4GH file, or update an old one lists the commonest findings and their fixes.

In the terminal

pedigree-ga4gh validate /data/examples/okafor_phenopackets-family.json
pedigree-ga4gh validate --json /data/examples/older/abusua2ga4gh-0.2_phenopackets-family.json | head -20

The exit status is 0 for a valid file and 1 for an invalid one. --json prints the findings as JSON. phenotk validate FILE runs the same checks on a file in the standard form; a file from an older tool it refuses, with a message saying to upgrade it.

In Python

import pedigree_ga4gh as pg

doc = pg.load("/data/examples/okafor_ga4gh-pedigree.json")
findings = pg.validate(doc)
print(pg.render_findings(findings))
print("valid" if pg.is_valid(findings) else "not valid")

Upgrade a file from an older tool

Earlier versions of our tools – studio2ga4gh up to 0.3, abusua2ga4gh up to 0.2 – wrote GA4GH files that the standard does not accept. The upgrade rewrites such a file, once, in the standard form, and lists every change it made and everything it could not do. It tidies other non-standard files too.

What it changes

  • The form: studio2ga4gh 0.3's GA4GH Pedigree, which was the conceptual model written out as JSON, becomes one Phenopacket per person, with relationships in the standard form.
  • What the standard has no place for: names are removed (Phenopackets have no field for a name, and names are personal data); diseases inside subject are moved to the Phenopacket; notes on relationships go into the narrative.
  • metaData: added where it is missing, with phenopacketSchemaVersion, and a resource for every ontology the terms use.
  • KIN: retired codes are replaced by the current ones, the people swapped where the new term runs the other way, and labels corrected; a relation whose code and label disagree is decided by its label (abusua2ga4gh's KIN:039 isSpermDonorOf becomes KIN:004).
  • Carriers: the phenotypic feature HP:0032500 written for a carrier is removed – it is Exacerbated by tobacco use – and a GA4GH Pedigree's narrative says who is a carrier.
  • Field names in proto spelling (index_patients) are written in camelCase (indexPatients), as JSON is.

What it leaves to you

Under to do, it lists what only a person can decide:

  • conditions with a name and no term: Fill in missing terms gives them their terms;
  • carriers in a Phenopacket or a Family: Phenopackets have no field for carrier status, and the only structured place for it is a genomic interpretation of the variant, if it is known (phenotk add --variant in the terminal: Add findings to people);
  • foster and social parents that abusua2ga4gh wrote as adoptive parents, which only the relationship's note tells apart;
  • for studio2ga4gh 0.3's GA4GH Pedigree, the conditions: it recorded who was affected, but not by what, so convert the drawing again or use the Phenopackets file made with it.

Nothing is guessed. A file that is already standard comes back as it was, apart from its field names. Under the result, Check the upgraded file runs the check on it.

In the terminal

pedigree-ga4gh upgrade /data/examples/older/abusua2ga4gh-0.2_phenopackets-family.json -o ~/results/abusua_phenopackets-family.json
pedigree-ga4gh validate ~/results/abusua_phenopackets-family.json

phenotk upgrade FILE -o OUT does the same.

In Python

import pedigree_ga4gh as pg

doc = pg.load("/data/examples/older/abusua2ga4gh-0.2_phenopackets-family.json")
new, changes, todo = pg.upgrade(doc)
pg.dump(new, "/home/user/results/abusua_phenopackets-family.json")
for c in changes:
    print("changed:", c)
for t in todo:
    print("to do:", t)

Compare two files

Lists what differs between two GA4GH or Phenopackets files – people, terms, relationships – leaving out the order of things and when and by whom the files were made, which change every time a file is written.

In the later version, the twins' hearing loss has been found to be sensorineural, so each has a second phenotype.

When to use it

  • To see what a conversion changed: a file and the same file converted to the other form and back.
  • To see what is new in a second version of a family's file.
  • To check that a de-identified or filtered file lost only what it should have.

Reading the result

A line for each difference, with its place in the files: proband.phenotypicFeatures: length 1 != 2, pedigree.persons[3].affectedStatus: 'UNAFFECTED' != 'MISSING' (the value in the first file, then in the second), narrative: only in A. De-identify

Makes a copy of a GA4GH or Phenopackets file for sharing: everyone gets a new id, used consistently everywhere in the file, and dates of birth, other ids and, if you like, who made the file are taken out. The key from the old ids to the new ones can be kept in a file of its own.

The form

New ids
IND-0001, IND-0002 … in the order the people come in the file; codes made from the old ids (such as IND-3f9a1c2b7d40), which with the same secret are the same in every file, so that the same person can be followed across files without their id; or the ids as they are.
Secret for the codes
Any words, kept private. Without a secret, anyone with the old ids could make the codes again and so undo them.
Keep dates of birth, Ages
Dates of birth are taken out unless you keep them. The age at the last encounter can be put in bands of 5 or 10 years (47 becomes 45); ages of onset are left as they are.
Keep other ids
Other ids of a person (alternateIds, such as a hospital number) are taken out unless you keep them.
Hide who made the file, and when
The metaData must say who made the file and when, so instead of the original createdBy and created it says phenotk deidentify and the time of the de-identification; the record of updates goes.
Save the key as
A JSON file of old id → new id. Keep it apart from the shared file: with it, the new ids lead back to the old ones.

What changes in the file

  • The ids, everywhere: each Phenopacket and its subject, the relationships, the index patient, a Family's pedigree, biosamples, genomic interpretations and files.
  • The ids in a GA4GH Pedigree's narrative too (proband IV-3 becomes proband IND-0014). The narrative is free text, so read it before you share: the tool reminds you.
  • Nothing else: terms, sexes, relationships and the shape of the family stay as they were.
De-identified is not anonymous

This removes what the file says directly. A family can still be recognised from what is left – a rare condition, a large or unusual family, ages, the place it came from – especially by someone who knows it. Whether a file can be shared, and with whom, is for you to judge under your institution's rules, and the law, on patient data.

--keep-dob, --bin-age 5y|10y, --keep-names, --drop-provenancewhat is kept

Put files together

Merges Phenopackets, Families and GA4GH Pedigrees into one Cohort – a set of people who need not be related – or into one Family.

The form

The files
Two or more: add them one by one.
Into
a Cohort, such as the probands of several families, or a Family.
Its id, Save as
The new file's id, and where it goes.

Who ends up in it

  • A Cohort has every Phenopacket of every file. People are told apart by their ids, and pedigree numbers recur from family to family, so a person whose id another file has already used (IV-3, in two families) is renamed after their file's id: FAM2-IV-3. The tool says whom it renamed. Give each family its own id when you convert it (Family id, in Drawing → GA4GH), and the new names say which family each person came from.
  • A Family is one family, so the same id is the same person: the first Phenopacket for each is kept, and the tool says which were left out. The first file's first person becomes the proband. The Family's pedigree comes from the Families among the files, and from the GA4GH Pedigrees' relationships; anyone in neither is added as a founder (no parents).

The new file's metaData declares every ontology the files declare, with its release.

PED and MPED files

mpedtools works on PED files and on MPED files, which are PED files with a column for each of several conditions. Its five tools in the Tools tab summarise and check a file, take one condition out, put files together, split families apart, and turn one kind into the other.

The five tools

Summary and check
The families, people (founders and the rest, by sex), and for each condition how many are affected, unaffected and carriers; then the check: people listed twice, parents who are not in the file, parents of the wrong sex, status codes other than 0, 1, 2 and 3.
Take one condition out
A plain PED file for one condition of an MPED file (give its column name, as the file's first line or the summary shows it), or one for each condition if you leave the name empty. Carriers (3) become unaffected (1), since a plain PED file has no code for them.
Put PED files together
PED files of the same people, one condition each, into one MPED file; name the conditions in the same order as the files, or each is named after its file.
One file for each family
A PED or MPED file of several families, split into a file for each, named after the families' ids.
PED ⇄ MPED, and columns
Make a PED file an MPED file or the other way round (keeping one condition), or add or remove a condition column; a new column starts with everyone at the value you choose.

The GA4GH Pedigree

The Global Alliance for Genomics and Health (GA4GH) is writing a standard for pedigrees. This page says what that standard is so far, the form in which the workbench writes a GA4GH Pedigree, why, and what was wrong with the files our older tools wrote.

The standard, so far

The GA4GH Pedigree Standard is still in development. Its documentation describes a conceptual model: a pedigree is a set of individuals and the relationships between them, each relationship named with a term of the Kinship Ontology, KIN. It is not a file format of its own. It is carried by other standards, in two forms:

  • In Phenopackets. A new message, a Pedigree with its individuals as Phenopackets and its relationships named by KIN terms, was proposed for the Phenopackets schema in November 2022. The proposal was closed without being merged in September 2025, because the pedigree group had not yet decided. It is in no release of Phenopackets.
  • In HL7 FHIR, with a draft implementation guide.

Neither form is approved yet. The approved GA4GH format that the workbench writes is Phenopackets version 2: the Phenopackets Family, and the Phenopackets inside the GA4GH Pedigree.

The form the workbench writes

A GA4GH Pedigree from the workbench is the Phenopackets form of the proposal, written as Phenopackets' JSON is written (field names in camelCase):

{
  "id": "FAM1",
  "narrative": "Pedigree drawn in Pedigree Studio: 16 people; proband IV-3. …",
  "date": "2026-10-17",
  "indexPatients": ["IV-3"],
  "individuals": [
    {
      "id": "FAM1-II-3",
      "subject": {"id": "II-3", "vitalStatus": {"status": "ALIVE"}, "sex": "FEMALE"},
      "diseases": [{"term": {"id": "MONDO:0007254", "label": "breast cancer"}}],
      "metaData": {
        "created": "2026-10-17T09:00:00Z", "createdBy": "studio2ga4gh 0.4.0",
        "resources": [{"id": "mondo", "name": "Mondo Disease Ontology", "version": "2026-10-06",
                       "namespacePrefix": "MONDO", "iriPrefix": "http://purl.obolibrary.org/obo/MONDO_", …}],
        "phenopacketSchemaVersion": "2.0"
      }
    },
    …
  ],
  "relationships": [
    {"individualId": "I-1", "relation": {"id": "KIN:028", "label": "isBiologicalFatherOf"}, "relativeId": "II-3"},
    …
  ]
}
  • Every individual is a complete Phenopacket version 2, with its own metaData, so that everything about a person – sex, whether they are alive, diseases, phenotypes – is in an approved, checked structure. Only the wrapper, the list of individuals and the relationships, comes from the proposal.
  • Each relationship is one current KIN term, written once (a symmetric one, such as partners or twins, in one direction). KIN lists them.
  • People are named by their pedigree numbers (II-3) unless you choose otherwise. Names are never written: Phenopackets have no field for a name.
  • A condition with no ontology term is left out, with a note, because a disease or phenotype without an id is invalid.
  • What the standard has no field for – a carrier, a pregnancy, a symbol that stands for several people – goes into the narrative, so that it is not lost.

Why this form

  • The Phenopackets Family that goes with it is Phenopackets version 2 already, and the phenopacket toolkit is built around Phenopackets: one model throughout.
  • With each individual a Phenopacket, all that is said about a person can be checked against an approved schema, as the GA4GH's own validator checks it.
  • The standard's own examples use this form.

If the GA4GH settles on a different form, one module of the workbench's packages (pedigree_ga4gh) changes, and the upgrade rewrites files from this form.

One implementation

All of the workbench's tools read and write GA4GH files through one package, pedigree-ga4gh: studio2ga4gh, ga4gh2studio and the phenopacket toolkit can no longer disagree about the form. Its check applies the rules of the Phenopackets schema and of phenopacket-tools, the GA4GH's validator, and those of the pedigree (Check against the standard).

Before, studio2ga4gh and abusua2ga4gh each wrote GA4GH files their own way, and the phenopacket toolkit had a “dialect” for reading each. Neither way was correct:

Phenopackets

Phenopackets are the GA4GH's approved standard for a person's clinical findings – their phenotypes, diseases, and the genetic findings behind them – in a form that computers can read. Version 2 is the current one, and it is what the workbench writes.

The three messages

A Phenopacket
One person: the subject (id, sex, vital status, age), their phenotypicFeatures (HPO terms, observed or excluded, with onset and severity), diseases (Mondo terms), interpretations (genetic findings), and metaData.
A Family
One family: the proband and the relatives with findings, each a Phenopacket; a pedigree of everyone, in the form of a PED file (family, person, father, mother, sex, affected status); consanguinousParents, whether the proband's parents are related; and its own metaData.
A Cohort
A set of people who need not be related, each a Phenopacket.

What the workbench puts in a Family

  • The proband is the drawing's proband (the index patient); the relatives are the other people with a condition. A relative with nothing to record is in the pedigree but has no Phenopacket.
  • The pedigree's parents are the genetic ones: biological parents, and egg and sperm donors. Adoptive, foster and step-parents are not genetic parents, and are not written there.
  • consanguinousParents is worked out from the relationships: true when the proband's parents are marked consanguineous or share an ancestor.
  • Each Phenopacket has its own metaData, and so has the Family.

metaData and resources

Every metaData says when the file was made and by what (created, createdBy), the schema version (phenopacketSchemaVersion: 2.0), and a resource for each ontology whose terms it uses, with that ontology's release:

"resources": [{"id": "hp", "name": "human phenotype ontology", "url": "http://purl.obolibrary.org/obo/hp.owl",
               "version": "2026-09-01", "namespacePrefix": "HP", "iriPrefix": "http://purl.obolibrary.org/obo/HP_"}]

Every term's prefix (HP in HP:0000365) must be declared there: that is the rule of phenopacket-tools that files most often break. The release comes from the terms file, the ontology file searched, or EBI's service; it is unknown when none of them says.

In JSON

Phenopackets are defined in Protocol Buffers, and written as JSON the way proto3 writes it: field names in camelCase (phenotypicFeatures), values that are their defaults may be left out, and readers accept the proto spelling (phenotypic_features) too. The workbench writes camelCase and reads both.

PED and MPED files

A PED file is a pedigree as a table: one line per person, which linkage and association programs (and PLINK, as a .fam file) read. An MPED file is a PED file with a column for each of several conditions.

The columns

ColumnHolds
1 · familythe family's id: FAM1
2 · personthe person's id, unique within the family
3 · father, 4 · motherthe parents' ids, or 0 for a founder (no parents in the file)
5 · sex1 male, 2 female, 0 unknown
6 · status1 unaffected, 2 affected, 0 unknown
FAM1	I-1	0	0	1	2
FAM1	II-2	I-1	I-2	1	2
FAM1	III-2	II-2	II-1	2	2

The columns are separated by tabs or spaces. Some programs write -9 for an unknown status; the workbench writes 0, and mpedtools warns about -9 (an unknown parent may be -9 too, which it reads as 0).

MPED files

An MPED file starts with a line naming its condition columns, and has one status column per condition:

# MPED v1	Cystic_fibrosis	Carrier
# FamID	IndID	FatherID	MotherID	Sex	Cystic_fibrosis	Carrier
FAM1	Michael	John	p-jw	1	3	3
FAM1	Amelia	Philip	Ruth	2	2	1

In an MPED file, 3 marks a carrier. A plain PED file has no code for one, so a carrier becomes unaffected when one condition is taken out.

Which tool for what

  • A drawing → Drawing → PED or MPED, or through the GA4GH files: Make a PED file for a linkage program compares the two.
  • A PED file → a drawing: PED or MPED → drawing.
  • Checking, taking conditions out, merging and splitting: mpedtools.

Ontology terms and terms files

An ontology is a curated list of terms, each with an id, a label, a definition and its place among the others. GA4GH files name conditions by such terms, so that software everywhere reads breast cancer the same way, whatever it was called in the clinic.

The two ontologies

The Human Phenotype Ontology (HPO)
Signs and symptoms – phenotypes – such as HP:0000365 Hearing impairment. In a Phenopacket they are phenotypicFeatures, and can be marked excluded (looked for and not found).
The Mondo Disease Ontology
Diseases, such as MONDO:0007254 breast cancer, brought together from other disease vocabularies (OMIM, Orphanet, ICD and others). In a Phenopacket they are diseases.

Use a Mondo term when there is a diagnosis, and HPO terms for what was seen, with or without one.

Ids and releases

  • An id is a CURIE: a prefix, a colon and a number – HP:0000365, MONDO:0007254. (HP_0000365, as some web pages write it, is the same term; the workbench writes the colon.)
  • The ontologies are released every month or so; a term may change its label, and now and then is made obsolete and replaced. So each GA4GH file records the release its terms came from, in its metaData.

Where a condition gets its term

  1. In the drawing's colour key: an id in brackets after the name – Condition X [MONDO:0009061]. The drawing then carries its term wherever it goes. Match conditions to terms can write the ids into a copy of the drawing.
  2. In a terms file, given to Drawing → GA4GH or to Fill in missing terms.

The terms file

A JSON file that maps each condition's name, as the colour key has it, to its term. Match conditions to terms writes it, with each term's label and release:

{
  "Breast cancer": {"id": "MONDO:0007254", "label": "breast cancer", "version": "2026-10-06"},
  "Hearing loss from birth": {"id": "HP:0000365", "label": "Hearing impairment", "version": "2026-09-01"}
}
  • An id alone will do: "Ovarian cancer": "MONDO:0008170". Without a label, the condition's own name is used; without a release, it is recorded as unknown.
  • The names are matched without regard to case, so one terms file can serve many drawings of a project.
  • The log that Fill in missing terms writes (….log.json) can be used as a terms file too.

Looking terms up

The HPO and Mondo can be searched on their own sites, on EBI's Ontology Lookup Service, or here with Match conditions to terms – online through EBI, or offline in copies of the ontologies (hp.obo, mondo.obo). Give the conditions ontology terms has advice on choosing.

Privacy

The workbench is a web page that does its work in your browser. Your drawings and files are not uploaded anywhere: there is no server behind it that sees them.

What stays on this computer

  • Your files, drawings and notebooks, kept in this browser's storage for the site (Your files).
  • The drawing on show in the Studio, kept by Pedigree Studio in the same storage.
  • Small settings: the tab you were on, the help page you were reading, the name you gave the terminal.

The page has no cookies, no accounts and no analytics.

Patient data

Pedigrees are personal data about whole families, including people who have not consented to anything. Use the workbench as your institution's rules on patient data allow, and:

  • prefer pedigree numbers to names: the GA4GH files use them by default, and the drawing is the only place names need to be;
  • check the ids of PED files made from drawings, which are the text under the symbols (Drawing → PED or MPED);
  • de-identify files before they leave you, and keep the key apart (De-identify), remembering that de-identified is not anonymous;
  • on a shared computer, download your work and use My files → Start afresh when you finish.

When something goes wrong

The common problems, and what to do about each.

Python does not start
Python is downloaded from cdn.jsdelivr.net the first time (about 10 MB). If the network blocks that site, or there is no connection, the tools, the notebook and the programs cannot run; the Studio and the Files tab still work. Try again on another network. After the first time, the browser usually keeps a copy.
“This GA4GH Pedigree was written by studio2ga4gh 0.3 or earlier …”
The file is in an older form, which the tools no longer read. Upgrade a file from an older tool rewrites it, once.
A condition is missing from the GA4GH files
It has no ontology term, so it was left out (the tool said so under its result). Give it a term with Match conditions to terms, and convert again with the terms file. Check that the name in the terms file is the name in the colour key; case does not matter, spelling does.
A colour is not counted as a condition
The colour key does not name it. Open the drawing in the Studio, click the key and type the condition's name beside that colour.
“EBI's Ontology Lookup Service did not answer”
The service is down or slow, or the network blocks www.ebi.ac.uk. Try again later, or search copies of the ontologies on this computer instead (2 · Search in).
The PED file has names as ids, or the same id twice
studio2ped uses the text under the symbols as ids. Change the labels in the drawing, or make the PED file through the GA4GH files, which use pedigree numbers (Make a PED file for a linkage program).
The drawing a tool made looks untidy
Press Tidy in the Studio tab, or tick Lay it out afresh with Pedigree Studio's Tidy before running the tool.
The Studio tab shows the wrong drawing, or none
The bar above it says which file the drawing on show belongs to. Open… shows any of your drawings; the file button lists the latest.
A tool waits for a long time
A notebook cell may be running: the tools share the notebook's Python, and wait for the cell to finish (stop it in the Notebook tab). The first search of a local copy of Mondo also takes a while: it reads the whole file.
hponorm or mondonorm stops at once in the terminal
They ask questions that this terminal cannot answer. Give them the answers in a file, or use Fill in missing terms or Match conditions to terms (The Terminal).
My files have gone
Are you in the same browser, on the same computer, and not in a private window? The files are kept by the browser for this site only. A browser that clears site data when it closes deletes them too: download what you want to keep.
“The workbench is open in another tab or window too”
Both tabs keep files in the same place, and one can overwrite what the other saved. Close one of them.

Reporting a fault

If a tool fails with Python's traceback (under the result: Python's traceback), or a file the workbench made does not pass its own check, that is a fault. Report it on the workbench's issues page, with the traceback and, if you can, a file that shows it – an example, or a de-identified copy of yours. Never attach a family's real data.
